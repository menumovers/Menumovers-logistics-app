## 1. `replit.md` (or `CLAUDE.md` / `PROJECT.md` — whichever is the LLM context file for this environment)

This is the master file, loaded at the start of every session. Structure it as:

### Overview
One paragraph: what the product does, who it's for, what problem it solves.
Be specific about scope — what this codebase handles and what it does NOT handle.

### Hard Policies
Non-negotiable constraints derived from the product's nature. Examples:
- Guest access requirements (can unauthenticated users do X?)
- Data ownership rules (who can see whose data?)
- Any regulatory or legal constraints already present in the code

### The [Project Name] Guardian
Define the LLM's role explicitly:
- Title: "Lead Architect for [Project Name]"
- Mission: prevent [specific failure mode] by enforcing [specific principle]
  (e.g. "prevent plausible tech debt by enforcing centralized utilities")
- List 3–5 numbered rule categories, each with 2–4 concrete sub-rules.
  Base these on patterns already in the code — auth flows, calculation logic,
  time/locale handling, external service calls, etc.
- Add a "Hard Constraints / No-Go Zone" section for things like `as any`,
  unsafe parsing, or any pattern you've already decided to avoid.

### Pattern Enforcement Table
A table mapping "if you are touching X" → "use this file/function".
Populate it from the code that exists now. Mark it "(non-exhaustive — see SSOT doc)".

### System Architecture
- Tech stack (runtime, frontend, database, auth, payments, hosting)
- Core architectural decisions: list each one with a one-sentence rationale.
  Focus on decisions that constrain future work (monolith vs. microservice,
  polling vs. websockets, server-side vs. client-side validation, etc.)
- Database schema location and migration workflow

### Documentation Conventions
One line per document explaining its purpose and when to consult it.  
Enforce updating of all relevant documentation after completing tasks.

### External Dependencies
List each external service with: name, purpose, which env vars configure it,
and whether it's live or in-progress.

## 2. `docs/architecture_sources_of_truth.md`

This is the SSOT registry. For each piece of business logic in the codebase that
could be duplicated or re-implemented by a future LLM:

- **Name** the utility / function / module
- **Location**: exact file path and exported name
- **What it does**: one sentence
- **Formula or logic** (if it's a calculation): write it out explicitly
- **Callers**: list the files that use it now
- **Do not**: describe what NOT to do instead of using this SSOT

Group these into logical categories (e.g. Calculations, Auth, Time/Locale,
External Services, Data Access).

Add a **Route Modules** section if routes are split across files — table of
module → endpoints → how it's registered.

Add an empty **Change Log** section at the bottom with today's date and a note
about the initial documentation pass.
